# ADR-001: MPU6050 独立软件 I2C 总线（PB10/PB11）

## 状态

Accepted（2026-09-06）

## 背景

MPU6050 与 SSD1306 OLED 都需要 I2C 通信。STM32F103C8T6 有 I2C1（PB6/PB7）和 I2C2（PB10/PB11）两个硬件 I2C 外设，但项目里 OLED 已用软件 I2C 在 PB8/PB9（沿用 adc-oled 的 MyI2C.c）。

## 决策

**MPU6050 使用独立的软件 I2C 总线，PB10=SCL, PB11=SDA，与 OLED 共享 I2C 时序实现但不复用代码。**

- OLED 软件 I2C：PB8/PB9，100kHz（沿用 adc-oled）
- MPU6050 软件 I2C：PB10/PB11，400kHz（独立快档）

## 原因

1. **代码解耦**：MPU6050 的通信模式（地址探测 + 写寄存器 + burst 读）与 OLED（命令 + 数据流）差异大，独立实现便于单测和维护
2. **速率独立**：MPU6050 100Hz 采样需要 400kHz 才不阻塞；OLED 100kHz 已经流畅
3. **总线隔离**：双 I2C 总线互不干扰，单一时刻只有一条在驱动，软件 I2C 无冲突风险
4. **避开硬件 I2C1 的坑**：F103 的硬件 I2C 历史上 ARLO/BUSY 问题多（gcc-toolchain-migration 笔记），软件 I2C 更稳

## 后果

- 4 个 GPIO（PB8/9/10/11）被软件 I2C 占用，但 F103C8T6 引脚充足
- 两条软件 I2C 维护成本：mpu6050_i2c.c 是 MyI2C.c 的 1:1 副本（仅引脚 + 延时不同）
- 未来若加第 3 个 I2C 设备，需要再写一份；可重构时抽 `soft_i2c_bus_t` 结构体

## 替代方案

- **A. 硬件 I2C1（PB6/PB7）+ 软件 I2C PB8/PB9 OLED**：硬件 I2C 坑多，调研已证
- **B. 共享 PB8/PB9 总线（OLED 与 MPU6050 共线）**：地址冲突风险 + 通信调试复杂
- **C. 硬件 I2C2（PB10/PB11）+ 软件 I2C PB8/PB9 OLED**：与 B 同坑
