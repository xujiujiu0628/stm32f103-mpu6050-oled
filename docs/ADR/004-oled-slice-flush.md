# ADR-004: OLED 整帧刷改分片刷（不引入 RTOS）

## 状态

Accepted（2026-10-26）

## 背景

OLED 走 100% 软 I2C（PB8/PB9），每次刷新整帧 1024 字节。2026-10-26 用 DWT 周期计数
在 `My_OLED_Update` 前后实测（RTT 1s 一行 `[PERF]` 心跳）：

| 观测项 | 整帧刷（改动前） |
|---|---|
| 单次刷屏阻塞 | **132.1ms / 帧**（等效总线 ≈63kHz、128µs/字节） |
| 主循环迭代 | 7 次/s，其中"未刷屏的轻迭代" **0** 次 |
| 实际 MPU 采样 | **7.3Hz**（名义 100Hz，间隔均值 137ms） |
| OLED 帧率 | 7fps（名义 10Hz） |

推论：整条主循环是"采样 → 刷屏"的串行链，一个迭代只剩一次采样机会。
而 `Tetris_Tick` 内部按"每次调用 = 10ms"写死累加（`+= 10 / -= 10`），
于是标称 500ms/格实际走 ~7 秒/格 —— 这是"手感不流畅"的真因，与是否抢占式调度无关。

> 顺带订正：`User/MyI2C.c` 原先写的"3µs≈330kHz / 整帧 1KB 从 25ms 降到 13ms"是**误记**，
> 从未实测过（3µs 位延时 × 8192 位已 ≥74ms，13ms 数学上不可能）。已按实测改写。

## 决策

**把整帧刷切成 16 片 × 64 字节，每个主循环迭代只发一片**（`User/oled_view/oled_view.c`
的 `OLEDS_SLICE_ENABLE = 1`，默认开）。驱动侧新增两个最小原语：

- `My_OLED_UpdateChunk(page, col, len)`：发某页的 `[col, col+len)` 一段（页内列地址由 SSD1306 自增）
- `My_OLED_SetCursorFast(x, page)`：把 3 条定位命令合并进 1 个 I2C 事务（`Co=0` 连续命令），
  每片省 ~0.4ms 事务开销

一次性路径（启动画面、校准提示覆盖层）**保留整帧刷**：校准场景本来就要求"先刷完屏再采样"，
把刷屏成本花在校准之前，避免污染采样 dt（09-06 已踩过的坑）。

## 原因

1. **阻塞点不在优先级，在单次同步事务的长度**：切片把最坏阻塞从 132ms 降到 8.4ms，
   低于 10ms 采样闸门，采样节拍随即恢复 —— 这是任何调度器都给不了的效果
2. **零新依赖**：不引入 RTOS/任务栈/临界区，flash 仅 +0.8KB，改动集中在 `oled_view.c` + 两个驱动原语
3. **可逆**：`OLEDS_SLICE_ENABLE 0` 即回到整帧刷（A/B 对比与回归都靠这个开关）
4. **采样率是互补滤波的前提**：dt 有 0.5s 回退保护，但采样太稀会让加速度纠正被稀释（09-06 已验证过）

## 后果

实测（同一天，同一套探针）：

| 观测项 | 整帧刷 | 分片刷（现默认） |
|---|---|---|
| 单次刷屏阻塞 | 132.1ms | **8.4ms** |
| 实际 MPU 采样 | 7.3Hz | **96~97Hz**（avg 10.3ms / max 14ms / 漏拍 0） |
| 主循环迭代 | 7 次/s（轻迭代 0） | 102 次/s（轻迭代 97） |
| OLED 帧率 | 7fps | 5~6fps |

- 帧率**下降**是切片的代价：每片多一次定位事务，且片与片之间被采样/按键插队。
- **NFR-01 的"OLED 刷新 10Hz"因此仍未达**（改动前 7fps 也没达），登记为已知欠账，
  提速路径见下方替代方案 D。NFR-01 的"MPU 采样 100Hz"由分片刷恢复。
- 俄罗斯方块节拍恢复到规格（0.5s/格），倾斜侧移判定跟随 96~97Hz 采样。
- 机械判据：`expectations.json` 的 `NFR-01` 断言 steady-state 1s 窗口 `mpu n ≥ 90` 且
  `max_us < 10000`；把开关拨回 0 会立即判红（132103µs 超界）。

## 评估过的替代方案

- **A. 引入 FreeRTOS（高优先级采样任务 + 低优先级刷屏任务）**：能修抢占，但刷屏**总时长和 CPU 占用率都不变**，
  帧率仍 7fps；还要处理 HAL SysTick 与 RTOS tick 冲突（`HAL_ADC_PollForConversion`/`HAL_SPI_Transmit` 的
  timeout 都吃 HAL tick）、共享缓冲临界区、+8KB flash。对"单一阻塞源"是过度设计 —— **不采用**。
  若将来真要多路独立周期任务（语音/串口协议/多传感器），再重审。
- **B. 硬件 I2C + DMA**：收益最大（整帧可降到 ~1ms 量级，且几乎不占 CPU），但 F1 的 I2C 外设坑多
  （errata + 从机时钟拉伸），需要专门一轮，**暂缓**。
- **C. 脏页刷新**：状态 0/1 常有 2/8 页整帧不变，最多省 1/8 字节量；与切片叠加的收益小于新增的状态机复杂度，**不采用**。
- **D. 提速位翻转**（MyI2C 用 BSRR 直写替代 `HAL_GPIO_WritePin`，位延时 3→2µs）：与切片正交，
  按实测反推（每字节 128µs 里约 6.8µs/位是 HAL 调用开销）估算整帧可降到 ~40ms、单片 ~2.5ms，
  届时片长可加大到 128 字节、帧率回 10fps 以上。风险是时序更紧凑可能花屏，**列为下一轮候选**。

## 风险

- 切片发送期间**禁止重绘缓冲**：用 `s_flush_pending` 做互斥，重绘必须等整帧发完（否则撕裂）
- 一次性整帧刷会作废未发完的片（`oled_flush_full()` 清 pending），否则同一帧会重复发一半
- 切片只改**发送顺序**不改内容，但"屏上看起来对不对"仍需人眼确认（SSD1306 页内列地址自增的假设）
- 若后续把 `OLEDS_SLICE_BYTES` 加大到 128，单片阻塞 ~16.7ms 会重新压到采样闸门以上 → 采样跌回 ~50Hz，
  届时必须先做替代方案 D
